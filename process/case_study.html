01 — Problem

Every request goes to the expensive model by default

Most LLM-powered products start with a single model choice and never revisit it. Sonnet (or GPT-4o) becomes the default because it feels safe — and the cost difference stays invisible until the bill arrives.

At 100,000 requests/month across a product with five LLM features, routing every call to Sonnet costs roughly $216/month. The question I wanted to answer empirically: how much of that is for quality we're actually using?

Core hypothesis: Not all tasks need the same model. Classification, extraction, and standard summaries are well-defined enough that a smaller model can match frontier quality. Complex code and multi-step reasoning genuinely benefit from higher capability. If we can measure that gap, we can route automatically.

What I measured

Dimension Why it matters in production
Quality Relevance score (LLM-as-judge) + hallucination rate — the two things routing can degrade
Cost per request Input vs output token pricing differs 4–5×; task type changes the ratio significantly
Latency per step Routing adds a classify step; must stay sub-ms to be invisible to end users
Token usage Output-heavy tasks (code) cost much more than input-heavy ones (classification)
Error taxonomy Timeout / context_length / quality_fail / hallucination — needed for SLA monitoring

02 — Approach

Two-dimensional routing: task type × complexity

Task type alone isn't enough. The same task can span a 10× cost range depending on how hard the instance is. Adding a complexity dimension makes routing precise.

Task taxonomy

Task type Production analog % of volume Default model
Classification Intent routing, ticket triage, sentiment ~30% Haiku
Simple Extraction Form parsing, entity extraction, data normalization ~20% Haiku
Summary Call transcripts, support threads, news digests ~25% Haiku standard
Code Generation IDE assistants, code review, test generation ~10% Haiku simple
Complex Reasoning Root cause analysis, strategy recommendations, audits ~15% Sonnet

The routing function

The core logic is a simple two-parameter function. The classifier runs in <1ms (pure regex) and adds no perceptible latency.

def select_model(task_type: str, complexity: str) -> str:
    """Select the most cost-effective model for the task."""

    # Classification, extraction — Haiku always (no reasoning chain needed)
    if task_type in ["classification", "simple_extraction"]:
        return "claude-haiku-4-5-20251001"   # $0.80/1M input

    # Summarization — Haiku for standard docs; Sonnet only when complexity == "high"
    if task_type == "summary" and complexity != "high":
        return "claude-haiku-4-5-20251001"   # meeting notes, reviews, news

    # Code generation — start cheap, upgrade on complexity
    if task_type == "code_generation":
        if complexity == "simple":
            return "claude-haiku-4-5-20251001"   # boilerplate, one-liners
        return "claude-sonnet-4-6"            # refactoring, API design

    # Complex reasoning — always Sonnet (hallucination risk too high on Haiku)
    if task_type == "complex_reasoning":
        return "claude-sonnet-4-6"

    return "claude-haiku-4-5-20251001"  # default: start cheap

Haiku matches Sonnet on most tasks — the gaps are predictable

Key insight — code generation is the clearest split case. Simple scripts (boilerplate, one-liners) show a 0.00 quality gap → route to Haiku. Hard instances (refactoring, multi-file debugging, API design) show an 18-point gap → route to Sonnet. This is exactly where the complexity dimension pays for itself.

Four things the benchmark confirmed

1. Classification & extraction: free savings

Zero quality gap at both difficulty levels. These are the 50% of call volume where routing to Haiku costs nothing in quality — just $0.80/1M instead of $3.00/1M.

2. Summary is threshold-sensitive

Hard summary (gap = 0.10) sits exactly at the default threshold boundary. For customer-facing legal summaries, pass complexity="high" to force Sonnet regardless of the global threshold.

3. Complex reasoning: always Sonnet

Haiku's hallucination rate is too high on multi-step analysis. The quality gap holds at both difficulty levels — this is not a threshold decision, it's a capability boundary.

4. Haiku is 2× faster on every task

Latency advantage is consistent and compounds at scale. At 100k requests/month, routing to Haiku where appropriate also means faster p95 response times across the product.

04 — Impact

Three cost levers, one framework

Routing is the biggest lever, but two others compound it. All three work independently and can be applied in sequence.

−70%
Model routing
Route classification / extraction / standard summary to Haiku. Biggest single lever — applies to 80% of call volume.
−5%
Prompt optimization
Remove redundant context, tighten system prompts. −20% input tokens × input price. Compounds on top of routing savings.
−18%
Output control
Set max_tokens per task type. Output costs 4–5× more than input — code generation and reasoning are the highest-impact targets.

A routing table set from benchmark data is only as good as the quality signal feeding it back. Three metrics trigger a routing review.

06 — Limitations

What this benchmark doesn't tell you

Small sample size

3 runs per task × difficulty cell is directional, not statistically significant. Shadow-test routing decisions on real production prompts before fully committing.

Synthetic benchmark prompts

Real production prompts may have different distributions — especially for complex reasoning and legal summaries. The benchmark establishes the framework; production data validates it.

Complexity detection is heuristic

Keyword signals and prompt length are imperfect proxies. Passing complexity explicitly from the calling service (e.g., user uploaded a PDF flag) is more reliable than inferring it.

Single-turn only

All benchmark calls are single-turn. Multi-turn conversations with accumulated context may behave differently — particularly for reasoning and code tasks where prior context matters.
